### 3.4 行业基线（沉淀前对标——防规则滑向项目特有）

| 维度 | 行业通用做法 | saas-cashier 对照 |
|---|---|---|
| 幂等键 | **Stripe `Idempotency-Key`**（header，后端存请求+响应 24h，同键重试返首次结果）/ Square body `idempotency_key` / PayPal `PayPal-Request-Id`；IETF httpapi 草案标准化中。实现标配 = 原子查重（DB 唯一约束 / Redis SETNX）→ 处理 → 存结果 | requestPayId 键已有，**后端创建路径不查重**——行业标准下等于没有幂等（键落库当查询键） |
| 责任分界 | **幂等是后端责任；前端防重只是体验优化与减载** | 三层全落前端，后端仅业务单据幂等（busiOrderId+payId，近似 DB 唯一约束兜底但未核实索引存在） |
| 不可逆操作 | **auth（授权可 void）→ capture（请款不可逆）** 两段；券/库存/票务 **reserve → commit/release**；长流程 **Saga + 补偿事务**（失败必有补偿动作） | verificationCouponFirst 一步 commit，无 reserve 态、无补偿路径——「先核销」问题的行业修法即此 |
| 重试 | **非幂等请求禁自动重试**；超时状态未知走**先查后发** + 对账（reconciliation）兜底 | 重试白名单制 ✅ 同款；先查后发已有雏形（queryPayResult 反查）；对账系统未核 |

结论：三层口径与行业同构、重试白名单是行业共识；差距集中在**后端幂等责任**与**两段式时序**两点——正是草稿①的定位句与草稿③ INV-PAY-002 的立论依据。

## 防重三层口径
判定线：**响应成功即改变后端资金或券态的接口**（收款/退款/撤销/反结账/核销/订金退；查询类不算）。
1. **请求号**：客户端生成入 body（如 requestPayId），每次发起新建
2. **在途锁**：内部标志位，进行中再次触发静默忽略——**内部守卫优先于 UI disable**
   （UI 态可被绕过/可点穿；git 实证：UI disable 路线被否决转内部锁）
3. **loading 遮罩**：barrierDismissible:false——辅助层，单独不算防重

⚠️ 三个易错认知（均生产实证）：
- **请求号 ≠ 幂等**：后端创建接口必须按请求号查重拦截才构成幂等——只落库当查询键 = 没有防重
  （实证：saas-cashier 后端落库 requestPayId 但创建路径未校验，幂等实依赖业务单据）
- **UI 防抖 / 结果列表去重 = 防重复显示**，不是防重请求
- **锁放finally**：在途锁必须在成功/失败/超时全路径释放，漏放 = 一次性卡死入口

## 不可逆操作时序
核销/扣款类不可逆操作不得先于支付确认，除非走「锁定 → 支付确认 → 核销 / 可撤销」两段式；
先核销流程必须有对客可见的撤销路径。
（行业同构：卡支付 auth（可 void）→ capture（不可逆）；券/库存 reserve → commit/release；
长流程 Saga + 补偿——失败必有补偿动作）
