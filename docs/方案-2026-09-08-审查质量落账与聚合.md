# 方案：审查质量落账与聚合（review 裁决终态可量化）
> 状态：已核验 · 随 1.0.3 落地 · 2026-09-08 · 关联：1.0.2 评审「方法论弱在主动提质」条 · 面向对象：维护者
> 核验注记（主会话 2026-09-08）：四处现状锚点全部属实；C1 flock 表述与 §5「常驻 0」两处措辞已按核验修正；A1 字段计数 七→八

## 1 目标与范围

**要解决**：reviewer（含 plan-reviewer）发现的**裁决终态无记录**——需求方每一次「采纳 / 改写采纳 / 误报 / 撤条」的判断用完即弃，只留主观复盘印象 → 误报率 / 采纳率不可算 → 审查纪律修订（reviewer.md）无数据依据。

**不做什么**：
- 不做看板 / 五维雷达类治理体系（README「治理从简」裁决不动摇——本方案是给该裁决留的**最低成本出口**，非推翻）
- 不做自动改规则（聚合结论只作 distill 提名素材，落盘走闸、需求方拍板）
- 不新增常驻命令 / 常驻 token（ledger 是文件不是常驻）

## 2 核心决策

| # | 决策 | 一句话理由 |
|---|---|---|
| C1 | **裁决即落账**：需求方对 review 发现的每次裁决，主控追加一行 JSONL 到 `.claude/memory/.review-ledger`（append-only，不进 git） | 与 `.pending-updates` 同 append-only 模式（主控会话内串行追加，无 hook 并发面，**不设锁**——flock 是 pending-updates 的 hook 并发需求，此处无此面） |
| C2 | **产生端只改格式不加机制**：reviewer.md 输出格式 ①~④ 追加发现编号（R1/R2…），使裁决可按条回指——「已验证（file:line）/ 推断（验证路径）」字段**已存在**，缺的只是可回指 id | 数据结构已在，只补胶水 |
| C3 | **聚合挂 distill §7 收尾，不建新命令**：读 ledger 算四数——总发现数 / 采纳率 / 误报率（误报+撤条占比）/ **按验证状态分桶的误报率** | 「推断」级发现被证伪比例才是指导修订的真信号；复用既有闸时序 |
| C4 | **闭环回闸**：聚合结论（如「推断级误报率 >50%」）按 distill 既有五问入闸，落点=reviewer.md 审查纪律条目修订（走闸） | 观测→修订走同一制度通道，不开旁路 |
| C5 | **样本量诚实线**：单项目 ledger <30 条不输出比率、只列明细 | 防小样本 Goodhart 化 |
| C6 | **写侧放交付汇报时序，不设 hook**：裁决语义事件（hook 感知不到）落 CLAUDE.md §五收尾时序「裁决完顺手一行」 | 同 pending-updates 哲学：把记忆问题变成看得见的待办，但此事件只能由主控判 |

### ledger 行格式（JSONL，一行一裁决）

```json
{"date":"2026-09-08","agent":"reviewer","fid":"R2","sev":"🔴","level":"L1","verified":"推断","verdict":"误报","note":"Dio 层不重抛，5 行核实证伪"}
```

- 字段：日期 / 出报告的 agent / 发现编号 / 严重度（🔴🟡🟢）/ 可达性（L0-L2，未定标 `-`）/ 验证状态（已验证·推断）/ 裁决（采纳·改写采纳·误报·撤条·搁置）/ 一行注记（可空）
- `verdict=误报` 且 `verified=推断` 的行是核心资产；`搁置` 不计入任何比率分母

## 3 现状（问题链）

```text
reviewer 输出发现（含严重度/L级/验证状态）→ 主控汇总上报 → 需求方逐条裁决 → ❌裁决终态流掉
→ 主观复盘（如 saas-cashier 报表 review 单点证伪「若 Dio 层抛出」）→ 无累积 → 纪律修订凭印象
```

证据存量：reviewer.md 审查纪律已含「假设性发现标验证状态」（saas-cashier 实证条）——单点教训已机制化进纪律，但**教训的产生路径本身无记录**，同类教训仍靠下一次人工撞见。

## 4 目标方案（三处改动）

| 改动点 | 文件 | diff 方向 |
|---|---|---|
| ① 发现编号化 | `agents/reviewer.md` 输出格式节 | ①~④ 前加「R<n> 编号」；输出格式示例同步 |
| ② 裁决落账时序 | `app/CLAUDE.md` + `plugin/CLAUDE.md` §五（孪生节，D1 断言覆盖面内——同源对照改） | 交付汇报必含「review 裁决回填」一行：逐条写 ledger（复用「沉淀候选提示」同款一行式） |
| ③ 聚合步骤 | `commands/distill.md` §7 收尾 | 加一步：读 ledger → 四数聚合（<30 条列明细）→ 异常模式作提名进 §5 闸；聚合输出进汇报，**不常驻任何文件** |

双模板孪生断言（test-self.sh D1）与语义闸不受影响：§五条数变更双侧同步即可。

## 5 影响面

- 用户 / 需求方：每次裁决多一个「回车确认落账」动作（主控代写，人只裁决）
- 已有流程：distill 收尾 +3 行步骤；reviewer 报告 +1 编号列
- 常驻 token：**≈1 行噪声级**（ledger 不 @import；reviewer.md 增 ~3 行属按需载入面；仅双模板 §五 裁决回填一行进常驻——14.4K 口径测不出）

## 7 分阶段落地

单批即落（改动面三文件 + 无 hook + 无 CI 新断言）；聚合逻辑先内联在 distill.md 流程描述（AI 执行），**不写独立脚本**——若日后聚合规则复杂化再考虑固化（治理从简同款延后）。

## 8 风险与回退

- **度量反身性**：AI 知误报率被观测 → 倾向少报压率。对策同 distill 蜜月期哲学：观测的是**模式**不是考核，裁决权始终在人；reviewer「只报不改」纪律不动
- **ledger 腐化**（裁决漏记）：写侧挂交付汇报时序是软约定——接受；漏记的损失只是样本变少，不产生错误数据（append-only，无污染面）
- **误报率武器化**（团队场景拿数字考核 reviewer）：注记 C5 样本线 +「不入 git」双保险，数字留在本机 memory 域
- **回退**：删 ledger 文件 + 撤三处 diff，零残留
