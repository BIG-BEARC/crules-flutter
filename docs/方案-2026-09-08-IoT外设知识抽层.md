# 方案：IoT / 外设通信知识抽层（S14 处置）

> 状态：讨论稿（待评审）· 日期：2026-09-08 · 关联需求：复审 S14 裁决（B 档：独立 references 文件）+ saas-cashier 8 类设备实证 · 面向对象：crules-flutter 维护者

## 1 目标与范围

**要解决什么**：backend.md 的「设备通信铁律」7 条是 IoT 领域知识而非角色定义——非 IoT 项目每次 spawn backend 拖 ~1/3 无关内容，IoT 项目真接设备时又远不够（8 类设备实证）。知识与角色分离：知识升格独立 references 文件（懒加载，非 IoT 项目零成本），角色卡留指针。

**不做什么**：不建独立 `iot` agent（YAGNI——references 层已零成本解决；升格触发条件写明留观）；error.md 与 backend.md 归并重复 3 条随本批一并处理；具体型号坑不预置（住消费工程 memory 坑库，框架级通用坑才进本文件）。

## 2 核心决策

1. **新增 `skills/flutter-rules/references/iot-devices.md`**：backend.md 铁律 7 条全量迁入「通用铁律」节 + 按通信方式分节框架（saas-cashier 实证设备归位），未实证分节**只立框架标「待项目沉淀」**——不杜撰内容（入预置门槛纪律）。
2. **分类三分**：外设类（蓝牙/串口/USB/网口——本文件主体）｜多屏类（副屏/数字客显——Flutter 多 window）｜独立 App 类（KDS/叫号大屏——**不是本机设备通信**，网络同步协议归 backend 网络域，本文件只留指针节）。
3. **backend.md 铁律节 → 一行指针**；error.md 与之重复的 3 条（一次性消费/重连 dispose/超时）指向同文件，不在两角色卡双份。
4. **SKILL.md 按域取用表 +1 行**（IoT/外设 → iot-devices.md）。
5. **agent 升格触发条件写文件头注**：多轮自持的 IoT 调试任务（协议调试+原生通道一体）实证后评估独立 `iot` agent——8 类设备已提前满足「量」的门槛，只差「任务形态」实证。
