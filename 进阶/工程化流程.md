# 工程化流程

> **fork 声明**：本篇 fork 自 crules `v74-fork-base`，由 crules-flutter 独立演进。

> **启用条件**：需求涉及新页面 / 跨模块 / 多端 / 大规模重构时复制本篇。极简改动（单字段、文案、明显单点修复）不适用，走 [`../CLAUDE.md`](../app/CLAUDE.md) §3 的简化流程。
> 配套根规则：[`../CLAUDE.md`](../app/CLAUDE.md)。本篇是根规则「需求 Gate / 方案 Gate」在大需求上的展开。
> 启用 superpowers / spec-kit 时，各阶段 skill 映射见 项目根 CLAUDE.md §九（superpowers + dart-flutter 协作）。

---

## 1. 何时用本流程

根规则 §3 的双 Gate 对所有非平凡改动适用。当需求规模升级到**新页面 / 新业务流 / 跨多模块或多端**时，需求 Gate 升级为分模块 PRD，方案 Gate 升级为带任务粒度的拆分计划，并在完成后走两阶段审查。

---

## 2. PRD（分模块设计文档）

> 启用 spec-kit 时，用 `/speckit` 产出 spec / constitution 作为 PRD，本节规定其**节奏**（分模块逐段确认）；未启用则人工产出 `prd-<feature>.md`。

主控（或 spec-kit）在需求讨论阶段产出 PRD，**按模块逐段展示并等需求方确认**，禁止一次吐完。

> **事实核验前移（v65）**：PRD 若基于调研报告转写，转写前先派核验代理**只核报告里的 `file:line` 事实**（不读方案，比方案评审便宜一个量级），设计建立在已核事实上——实战中转写引入的事实错误（键名 / 字段 / 常量值）占设计评审发现的一半，且全部可在此前拦住；与「二手摘要只用于定位」（根规则 §三）配套：摘要指路、核验代理证路、设计引用已证之路。**去转写（v66）**：核验后的调研报告直接作设计的事实小节（`file:line` 指针引用，不搬运内容）——报告进主线 + 转写再输出一遍是双重 token 损耗，且转写本身就是事实错误入口。

### 模块清单（按项目实际调整）

> 通用基线——模块按项目技术栈替换（纯后端 / 无 UI 项目可删「UI / 视觉」）。Flutter 专项补充（状态管理方案、federated 接口、`gen-l10n` 等）见 Flutter 规则包 checklist（crules 模板包同级 `../flutter/`，未安装则忽略）。

1. **架构概览** — 涉及哪些模块 / 目录 / 层级；是否新增入口 / 路由
2. **数据模型** — 接口字段、本地存储 Key、状态结构、是否新增实体
3. **业务 / 状态层** — 新增 / 复用的业务逻辑单元、依赖关系、生命周期
4. **UI / 视觉** — 页面骨架、复用组件、主题归口、暗黑 / 响应式适配
5. **国际化** — 新增文案 Key 列表（多语言同步策略）
6. **平台 / 原生差异** — 跨平台特殊处理（权限、后台、原生桥接）
7. **边界与失败** — Loading / Empty / Error / 超时 / 鉴权失效兜底

### 节奏

- 每段 200–300 字
- 需求方确认后再进下一段
- 全部确认后写入 `prd-<feature>.md`

## 3. 任务粒度

主控拆分任务遵循：

- **单任务 2–5 分钟可完成**，超过继续拆
- 每个任务**必须**带验证步骤清单（命令或可观察现象）
- 任务之间尽量无文件冲突，便于多个子 agent 并行派发
- **TDD 节奏按用例集分档**（v65，与 skill 逐用例默认的冲突按根规则 §2 优先级链处理——本包分档优先）：**同构用例集**（数据类 / 参数化 / 纯映射）批量红绿——全部用例写完 → 一轮 RED → 实现 → 一轮 GREEN，单点问题定向复跑；**设计驱动型用例**（会反过来改接口设计的）保持逐用例红绿。逐用例循环在同构集上是纯轮数浪费（实测 34 用例 ~60 轮，批量后 3 轮）。**批量 RED 须补偿断言有效性**：抽 1-2 个断言故意错值确认会红——逐用例红绿天然自证断言在测东西，批量化丢了这个自证，不补则恒真断言混入无察觉（v66）

### 任务模板

```markdown
## Task N: <任务标题>

**所属模块**：<模块名>
**主责 agent**：<角色，见 Agent编排.md>

实现要点：
- <要点 1>
- <复用现有 X，不新建 Y>

验证：
- [ ] 静态分析无 error
- [ ] 单测：mock 输入返回固定数据，结果字段齐全
- [ ] 异常路径返回错误状态
```

## 4. 方案评审（实施前）

PRD（§2）+ 任务拆分（§3）产出后、进入实施前，**停下来问需求方「是否派独立评审？」（默认必须派审，仅需求方明确跳过才跳过并记录理由）**，确认后派独立第三方 agent `plan-reviewer` 做方案技术评审。评审闭环、角色四分、流转、循环守卫、纪律全部见 [`方案评审闭环.md`](方案评审闭环.md)——本篇只规定**时机**；评审-裁决-修订全程 Plan 模式：

```text
方案成品（PRD + 任务拆分）→【确认点】问需求方是否派审 → 第三方方案评审 → 需求方逐条裁决 → 消解复审（diff 级，直到无须消解）→ ExitPlanMode 获批 → 落盘评审记录 → 实施
```

> 这是实施**前**的方案审；实施**后**的代码审见下一节「两阶段代码审查」。

---

## 5. 两阶段代码审查（编排时机）

代码完成后，由审查者分两轮独立审查。**审查的方法与纪律**见 [`审查与复核纪律.md`](审查与复核纪律.md)——本篇只规定时机：

- **第一阶段（规范合规）**：覆盖 PRD 功能点、边界、i18n、踩坑约束
- **第二阶段（代码质量）**：样式归口、状态管理、DRY、行数、复用
- 两阶段都通过后，主控才执行最终编译校验

## 6. Worktree 并行多功能

**同时开发 ≥2 个独立功能**时，用 worktree 而非分支切换，避免 IDE / 依赖安装 / 代码生成反复重跑：

```bash
git worktree add ../<project>-feature-a -b feature/a
git worktree add ../<project>-feature-b -b feature/b
# 各 worktree 单独安装依赖并打开独立 IDE 窗口
```

### 约束

- worktree 路径放在与主项目同级目录下，命名 `<project>-<feature>`
- 改了依赖描述或代码生成相关文件后，每个 worktree 各自重新生成
- 完成后 `git worktree remove` 清理
- **单功能开发不必 worktree**，正常分支即可

## 8. 合并纪律（跨分支协作）

- **合并前探对方基线**：先在对方分支跑静态分析 / 测试探基线——对方质量不可假设（不跑测试的提交、删码不删测试），合并 = 把对方技术债一次性接进自己分支，预留修复时间
- **格式化提交复活删除码**：合并含**全量格式化提交**的分支，冲突解决须逐文件对照双方意图——格式化让 git 失去行邻近性，「我方删除类」改动极易被带回

## 8bis. 深度实施纪律（根模板裁剪补遗，fork-coverage ✂️ 项归位）

> 以下 6 条在 crules 基线属根 CLAUDE.md §三，fork 根模板按密度精选裁至本篇——**效力等同根规则，大需求 / 高风险改动必查**：

- **二手摘要只用于定位**：调研报告、子代理摘要只能指引「去读哪个文件」；像素级 / 行为级实现必须打开一手源码
- **事实声明锚定出处**：设计 / 方案文档中的事实声明（接口路径 / 字段名 / 方法签名 / 资源存在性）必须附 `file:line` 出处，且当轮核对原值
- **新建前先查既有**：新建文件 / 字段 / 组件前，先检索工程既有等价物（调研是双向 diff：目标行为 + 既有资产）
- **语义以来源链为准**：标识符语义以值的来源链（追写入点）为准，不以命名推断；跨系统对字段核对两侧写入点
- **信任档位（提速档）**：扩大极简范围、免方案直接实施**仅凭需求方显式声明**生效（项目附录「协作偏好」或会话内明说）；AI 不得自行升档、不得据「最近没返工」推断已提速；连续返工时主动提示降档复查
- **工具降级**：`AskUserQuestion` / Plan 模式 / skill 不可用时降级为文本确认（编号选项 / 方案七要素列全后停下等回复），**须显式说明已降级**——降级不豁免 Gate 本身

## 9. 复刻 / 对齐任务的对照清单

复刻 / 对齐类任务（UI 对齐、跨工程移植、规范迁移）：方案 Gate 产物必须含**逐行对照清单**——基准值 / 当前值 / 动作三列，逐项注明基准出处 `file:line`；实施按清单执行，清单外改动按范围外处理。这是「参照物优先」纪律的**产物形态**（实战 3 轮 UI 对齐验证有效）。
