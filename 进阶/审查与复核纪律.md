# 审查与复核纪律

> **fork 声明**：本篇 fork 自 crules `v74-fork-base`，由 crules-flutter 独立演进。

> **启用条件**：项目需要 code review、资损评估、安全审计等「给出结论」的任务时复制本篇。
> 配套根规则：[`../CLAUDE.md`](../app/CLAUDE.md)。本篇不重复根规则（提交、范围、不虚构等），只补充审查的专门纪律。
> 启用 superpowers 时，两阶段审查叠在 `requesting-code-review` 上，skill 映射见 项目根 CLAUDE.md §九（superpowers + dart-flutter 协作）。
> **审代码（实施后）**：本篇审**代码**。实施**前**的**方案**审见 [`方案评审闭环.md`](方案评审闭环.md)。

## 核心区分

**【代码层面成立】≠【业务真实可达】。** 先验证业务场景，再定级。不得把「代码路径上能走通」直接当成「线上必现」。

---

## 业务可达性 Gate（上报前必过）

每一条审查发现，上报前**必须**回答：「它在真实业务流程中如何触发？」按可达性分级标注，禁止把低等级当高等级上报。

**定级前先查约束**（若启用记忆库）：`memory/business-rules.md`（业务规则——触发条件被否定 → 降级 / 撤条）+ `memory/INVARIANTS.md`（技术不变量——发现疑似破坏不变量 → 单列上报，不并入可达性定级）。

| 等级 | 含义 | 默认定级上限 |
|---|---|---|
| **L0 代码路径成立** | 仅静态推断能走通，未证实触发条件 | Low / 信息 |
| **L1 触发条件存在** | 有触发路径，但业务上是否存在该组合未证实 | Low–Medium，注明「待证」 |
| **L2 业务真实可达** | 已证实真实业务流程可触达，且无前置拦截 | 按实际影响定（**须需求方确认**） |

> **AI 能力上限是 L1**（触发条件存在）；L2（业务真实可达）是业务事实判断，不在 AI 能力范围，**必须需求方确认**。规则是「要求」不是「能力」——写「必须追到生效路径」≠ AI 真能追到代码之外的业务。未在 `business-rules.md` 沉淀的新业务，用疑问单上报（见下）。

- 「字段 / 变量用错」类发现，**必须**追到【它在生效路径上是否真的非空 / 被读取】，不得停在赋值处就定级。
- **必须**检查 UI 层是否已禁用该入口（`isGray` / `disabled` / 条件拦截），被拦截的路径不得按可达上报。

### 疑问单（新业务 / 未沉淀的可达性）

查 `business-rules.md` 未命中、AI 又无法自证可达性的发现，**不直接定级上报**，改用疑问单交需求方：

| # | 发现 | AI 的可达性判断 | 问需求方 |
|---|------|---------------|---------|
| 1 | <代码现象> | <L0/L1 + 为何到不了 L2> | 「此业务场景实际是否存在？入口是否触发？」 |

需求方判定后：不可达 → 撤条 + 沉淀 `business-rules.md`；可达 → 按实际影响定级。

## 子代理与工具结论复核

- 子代理、搜索工具、静态分析返回的发现是【**待验证的线索**】，不是结论。
- 主控上报前**必须**亲自读关键代码确认触发条件，不得整段搬运子代理的推测性表述。
- 复核范围：触发条件、前置拦截、字段在生效路径的读取情况、业务组合是否真实存在。

---

## 资损 / 金额类评级克制

- 资损、金额、库存等高敏感发现，评级尤其克制。
- 稳态流程走不到的路径，降到 Low / 边缘，并明确写出【为何测不出】的机制。
- **禁止**仅凭「代码能走通」或「字段值可疑」就定 Critical。

---

## 领域专家否决

- 需求方是该系统领域专家，业务可达性以其判断为准。
- 其明确指出某业务场景不存在、某入口不会触发时，直接撤掉该条发现，**不反复辩护**。
- 撤条时保留一句「经确认业务不可达」，供后续追溯；**同时沉淀一条进 `memory/business-rules.md`**（若启用）——把这次否决变成永久规则，下次同类问题自动消音。

## 两阶段审查（编排）

审查任务**分两轮独立输出**，不混在一起：

**第一阶段 — 规范合规（Spec Review）**：只看是否覆盖 PRD / 任务清单功能点；Loading / Empty / Error / 鉴权失效 / 超时等边界；i18n 是否多语言补齐；是否守住踩坑记录。**不评论**命名风格、不要求重构。

**第二阶段 — 代码质量（Code Quality Review）**：只看颜色 / 文本样式 / 间距是否归口；暗黑 / 主题 / 适配是否走统一扩展；状态管理用法与生命周期；DRY、命名、单组件行数；是否绕过现有抽象重复造轮子。**不再回头**讨论功能完整性。

所有 🔴（必须修）项修复后才算通过。

## Review Checklist（逐条对照）

> 通用条目，按项目技术栈裁剪。审查时逐条 PASS / FAIL + 原因，FAIL 项附修复建议（精确到文件行号）。

**0前. 验证事实纪律（根模板裁剪补遗，fork-coverage ✂️ 项归位）**：接口 / 数据结构以**真实响应**为准（真实抓包或运行日志确认，不从文档印象推测）；**构建 / 测试通过 ≠ 规范合规**——自定义 lint、主题 / 样式归口、控件选型等规范项常不在构建与测试覆盖内，须显式自查。

**0. 协作表达**：沟通简练精准；先给可执行结论；无废话 / 重复 / 过度铺垫。

**1. 架构合规**：遵循分层（表现层 → 逻辑层 → 数据层 → 网络）；表现层只渲染不做业务逻辑；每个视图只调自己的页面级状态 / 聚合层，禁止跨页或跨层直接订阅多个底层源；跨源组合经聚合层暴露；网络 / 存储走统一封装，路径 / Key 集中定义。

**2. 组件 / 视图设计**：拆分粒度合理（单组件约 200 行内）；复用组件归公共目录；间距 / 圆角 / 尺寸用约定值或主题常量；无硬编码颜色。> 框架专项（rebuild 优化、暗黑 / 主题扩展、颜色命名等）见 Flutter 规则包 checklist（crules 模板包同级 `../flutter/`，未安装则忽略）。

**3. 状态管理**：状态单元职责单一；生命周期合理（页面级 vs 全局单例）；非平凡实现已先获确认。> 异步三态、具体状态框架（Riverpod / Bloc 等）用法见 Flutter 规则包 checklist（crules 模板包同级 `../flutter/`，未安装则忽略）。

**4. 边界处理**：Loading 有反馈；Error 有用户可见提示；Empty 有占位；网络异常有兜底（离线 / 重试）；输入校验走统一工具；长操作（外设通信 / 上传 / 长连接）有超时与断连处理。

**5. 国际化**：用户可见文本走 i18n；新增 Key 同步多语言文件；必要时执行 i18n 代码生成。

**6. 代码规范**：文件头注释（如项目要求）；无调试日志（用统一日志工具）；无硬编码 URL / 密钥；命名规范；无新引入 lint 警告；import 分组有序。

**7. 功能完整性**：spec 功能点均已实现（非 stub）；用户可完成完整流程；关键路径无崩溃；新增入口 / 路由已注册。

**8. Git 规范**：commit message 清晰；不提交不该入库的生成文件；不提交调试临时代码。

## 审查汇报格式

```md
## 审查范围
- <模块 / PR / 版本>

## 发现清单
| # | 发现 | 可达性等级 | 定级 | 触发机制 / 为何测不出 |
|---|------|-----------|------|----------------------|
| 1 | <描述> | L0/L1/L2 | Low/Med/Critical | <证据或机制> |

## 已撤条
- <发现>:经确认业务不可达(<依据>)

## 复核说明
- 哪些发现已亲自读码确认触发条件;哪些仍为子代理线索待证。
```

## 案例 Why（不入正文，仅溯源）

一个连续称重功能的审查过判：① 重量字段存 total 非 delta 被当 Critical，实际后端不回传、试算回灌清空、删菜恒走 fallback；②「某核销入口绕过称重锚定」——业务上该核销场景根本没有称重菜；③「数量守卫缺失」——按钮已对相关商品禁用（`isGray`）拦截了点击。分别对应 L0→L2 误判、业务组合不存在、UI 拦截未查。沉淀为业务规则见 `memory/business-rules.md`（称重域示例 WR-WEIGH-001～003）。
