## 2 总评

机制设计 **A 级**：install 三态、真机 fixture 回归、twin 锚点 CI 守护、供应链自警、蒸馏闸五问——这些解决了多数 rules 仓库没意识到的真实难题（知识污染、孪生漂移、验旧不验新）。

三个结构性短板方向一致：**上下文经济学缺位于存量**（39.2KB 单 skill、22.5KB 常驻 CLAUDE.md，自家 §4.8 加法纪律只管增量不管存量）、**机制闭环有洞**（记忆库装完无接线、lint 基线含死配置且校验被静默关闭、漂移队列只管写不管读）、**内容时效无审计**（预设技术栈停留 2022-23 选型、坑库预置避重就轻）。

一句话：**把自己的哲学（按需加载、去重、真机验证、twin 守护）贯彻到自身最大的三处违反上**，是 0.5.0 最值得做的事。

## 4 发现清单

> 证据分级标签：【实测】= 本机实验/复现；【代码走读】= 源码可查；【判断·需核验】= 专业判断，按包纪律须查证后采信。
> 严重度：🔴 正确性/机制缺陷 ｜ 🟡 结构/成本风险 ｜ 🟢 打磨项。

### A 组 · 实测确认的机制缺陷

#### A1（🔴）lint 基线含死配置，且整文件的规则名校验被静默关闭

两条事实，均有实验证据：

1. **[analysis_options.yaml:25](../analysis_options.yaml#L25) 的 `cancelled_token_use` 不是合法 lint 规则名**【实测】。真机 analyzer 报 `undefined_lint`（见 §1 复现命令）；官方 linter 规则注册表（dart.dev，截至 Dart 3.13）亦无此名——它是 analyzer **诊断**（diagnostic）而非 lint 规则，写在 `linter.rules` 下是无效条目。意图落空：注释声称对应 checklist「边界处理类——异步纪律」，实际零拦截。
2. **[analysis_options.yaml:28](../analysis_options.yaml#L28) 的 `public_member_api_docs: false` 抑制整份文件的 `undefined_lint` 校验**【实测·bisect 定位】。最小 AO 文件含 `cancelled_token_use` 会报警；全量模板不报；逐项二分定位到该 map 形态条目（`- 规则名: false`）是抑制因子。连带后果：**未来本文件里任何规则名拼写错误都将静默通过**。规则本身仍是死配置——flutter_lints 4.0.0 的 `lib/flutter.yaml` 未启用 `public_member_api_docs`【实测 grep】，disable 一个没启用的规则是空操作（例外：消费项目自行叠加更严规则集时该行才生效，但那属于项目自己的配置职责）。

**影响**：模板自己的验收门是「`flutter analyze` 零 warning 才算过」，而基线文件自身埋着一处永远不被报告的配置错误；「规则工具化」（外审⑧）的基线可信度受损。讽刺点：0.2.3 F2 的教训是「测过了还要确认测的是真样本」——AO 的**落位逻辑**用真机 fixture 验了，AO 的**内容**从未过真 analyzer。

**修法**（P0，半小时）：删两行死配置；test-self 补一条「AO 内容真机验证」断言（flutter create 壳 + 拷模板 + `flutter analyze` 零 warning——无 SDK 的 CI 环境可降级为对 dart.dev 规则清单的离线比对），把 F2 教训补完闭环。

#### A2（🔴）记忆库装完即孤儿——NAVIGATION/MAINTENANCE 无任何加载接线

【代码走读 + grep 确证】[记忆库体系.md](../进阶/记忆库体系.md) 与 twin 表声称 NAVIGATION / MAINTENANCE「CLAUDE.md 引用，每次会话隐式加载」，但：

- [app/CLAUDE.md](../app/CLAUDE.md) / [plugin/CLAUDE.md](../plugin/CLAUDE.md) §十二只指向 `进阶/记忆库体系.md`（人读文档链接），**没有指向 `.claude/memory/` 的任何引用**，更无 `@import`（grep `NAVIGATION|@\.claude` 于两模板及 init.md 零命中，仅 update-memory.md 内部引用）
- [init.md](../commands/init.md) 三处必填引导（§七 / §十二 / 支持矩阵）**不含「记忆库接线」步骤**

且机制层面：CLAUDE.md 里的**普通 prose 提及不会加载文件**——Claude Code 的 CLAUDE.md 需 `@路径` 导入语法才真正内联。twin 表「加载时机」列当前是**期望而非事实**。

**影响**：8 个 memory 模板落位后，整套体系（找东西第一站、触发即更新纪律、`.pending-updates` 队列的存在前提——`pending-updates.py` 以 NAVIGATION.md 存在为启用判据）依赖一个不存在的引用。0.4.0 最大的新能力实际处于「装而不用」态。

**修法**（P0，一行 ×2 模板 + init 一项）：模板 §十二加三行 `@.claude/memory/NAVIGATION.md` 等 @import（init 步骤 4 同步加「接线确认」项）；twin 表「加载时机」列措辞同步为事实描述。注意 @import 的常驻成本（NAVIGATION 3.1KB + MAINTENANCE 4.5KB）应计入 §4.8 常驻预算——这正是 A2 与 B3 的交汇点，见 §5-P1。

#### A3（🟡）pending-updates 只闭环了写侧，读侧是纯软约定

【代码走读】[pending-updates.py](../hooks/pending-updates.py) 忠实记录漂移队列（含 flock 防并发，写侧工程质量好）；但消费侧是 [MAINTENANCE.md](../memory/MAINTENANCE.md) 自检清单的「会话收尾主控看到队列非空即提示」——**没有任何机制强制模型去看**。写侧有锁，读侧靠自觉。

**修法**（P1，小）：Stop hook 输出队列非空提醒（一行 echo 即可，无需 block 语义）；或最低限度把 `.pending-updates` 检查并入已有 Stop 场景。

### B 组 · 上下文经济学（存量豁免于自家 §4.8）

#### B1（🟡）SKILL.md 39.2KB / 850 行单文件，是最反 progressive-disclosure 的形态

【实测 wc】[SKILL.md](../skills/flutter-rules/SKILL.md) 39.2KB。skill 触发即**整文件**进上下文——问一个 Riverpod 问题，字体搭配（60-30-10 / 行高 1.4x）、WCAG 对比度、「背景加噪点纹理提升质感」全部拖入。文件头自称「按需加载的参考库，非常驻」，结构上却是单文件全量加载。内容构成问题更大：

- 约 60% 是 2026 年模型已内化的通用最佳实践（const 构造、`ListView.builder`、函数 ≤20 行、Effective Dart 链接）——对前沿模型边际价值≈0，纯 token 支出
- 「噪点背景」「多层阴影营造高级感」等视觉建议对业务 App 甚至有害
- 与 [设计方案 §4.8](设计方案-2026-09-04-易用性与知识沉淀体系.md) 加法纪律（新增 >5 行须懒加载方案）对照：**存量整体豁免**——skill 是基线 fork 起家，从未按该纪律审过

**修法**（P1，一周量级）：SKILL.md 瘦身为薄索引（~150 行：定位 / 优先级 / 方案骨架 / 配图约定 / 指针），内容按域拆 `references/` 分文件（style / theming / layout / docs-comment 各一）；**平台坑库独立成 skill**（它的触发场景「引依赖/升级/排障」与「写 Flutter 代码查规范」不同频，混载即浪费）；通用最佳实践删 60-70%，只留项目特有与非显而易见内容。代价要诚实记：skill 数量 ×2 后触发面维护成本上升（description 措辞要各自调好）。

#### B2（🟡）CLAUDE.md 常驻 22.5KB，§九/§十一速查表是双维护死重

【实测 wc】app 模板 22.5KB / 314 行每会话常驻。其中：

- [§十一 速查表（app:278）](../app/CLAUDE.md#L278)（16 行映射）维护的是**dart-flutter 插件的 skill 命名空间**——别家改名即全表腐烂，双模板各一份，比 memory twin 表更重的孪生**无人看守**。而模型本身按 skill description 自动匹配出场，人工映射表是负资产（唯一价值：给用户看的可发现性——这个价值放 README/help 更合适）
- [§九 superpowers×dart-flutter 分层表（app:242）](../app/CLAUDE.md#L242)每会话必载但低频使用，且对未装这两个插件的用户是死引用

**修法**（P1）：§十一降级进 skill 或 `/help`（保留 §十二一行指针）；§九压缩为两行心智模型 + 指针。预计常驻 -3~4KB/模板。与 §4.8 对齐：这不是新机制，是把「>5 行须懒加载方案」追溯适用于存量。

#### B3（🟡）§4.8 触发线已写死，但没有基线数字——触发条件等于未武装

【代码走读】设计方案 §4.8：轻量模式「不做」，触发条件写死（真实试点常驻 >15K tokens，或同一红线级规则被跳过 ≥2 次）。方向正确，但：**存量从未实测**（试点未启动，`/context` 快照无基线），触发是「>15K」而无人知道现在是 9K 还是 19K；「规则被跳过 ≥2 次」的记录载体（复盘记一行）也未有实例。

**修法**（P1，半天）：先测再说——任一真实消费工程跑一次 `/context` 记基线数（含本评审 A2 接线后的 NAVIGATION/MAINTENANCE 增量）；把数字写进 README 维护节，触发线才算武装。

### C 组 · 内容时效（判断·需核验，按包纪律附核验入口）

#### C1（🟡）预设 A 技术栈是 2022-23 的答案，且无对等审视机制

【判断·需核验】[app/CLAUDE.md §七 预设 A](../app/CLAUDE.md#L176) 推荐：`hive`（原作者已停更，社区延续为 hive_ce；或已到 drift/isar 时代）、`easy_localization`（长期低维护，主流已转向官方 gen-l10n / slang）、`flutter_screenutil`（平板/桌面多端争议大，纯 MediaQuery/断点方案更稳）、`retrofit`（声明式网络在 Flutter 生态已边缘化）。**本条最后核验：2026-09-04（判断来源：评审人经验，未逐项带 pub.dev 出处——按包纪律，采纳前请逐项核验）**。

结构问题重于个别条目：skill 坑节有「每次 minor 例行重验」义务，**预设栈没有对等机制**——而它影响每个新项目选型。

**修法**（P1）：① 预设栈逐项核验刷新（hive→hive_ce/drift 等按核验结论改）；② 把「栈审视」与坑节维护义务并列进 minor 例行；③ 预设条目加「最后核验」日期字段，与坑卡同纪律。

#### C2（🟡）预置坑卡避重就轻——三条高频官方明示坑缺席

【判断·需核验·入预置门槛候选】首批 3 卡纪律执行到位，但选题偏长尾（Win7），按包内门槛第②条（官方 issue / release notes 明示版本区间）以下三条全部合格且高频得多：

1. **Android 16KB page size**（Android 15+ 设备 / targetSdk 35+，Play 上架硬要求；对 **plugin 模板类型 A（带原生 .so）是发版阻断级**——比现有三条卡都高危）。核验入口：Android 官方 16KB 文档 + flutter/flutter 引擎相关 issue
2. **Android 15 edge-to-edge 强制**（targetSdk 35 起系统强制，自绘 UI 需处理 insets）。核验入口：Android 官方 behavior changes 文档
3. **Impeller 渲染器换代**（iOS/Android 先后默认启用，Skkia 时代的老绕法/性能 hack 失效，渲染类 bug 的归属判定基准变了）。核验入口：Flutter 官方 Impeller 文档 + release notes

**修法**（P1）：按坑卡纪律查证出处后预置（查不到出处不预置的红线仍守）；16KB 卡建议放 plugin 模板消费路径必经处。

### D 组 · 结构性风险

#### D1（🟡）双模板 §一~§六 是仓库最大的孪生，无 CI 守护

【代码走读】两份 CLAUDE.md 共享约 180 行红线/提交/双 Gate 内容（§一~§六），「两模板同源对照改」纯靠人记。**给 9 行 memory 表建了 twin CI 的体系，把最常编辑的两份 300+ 行文件留在人肉同步态**——这是自家哲学最明显的未贯彻处。0.4.0 CHANGELOG「两模板同源对照改」出现两处，人肉纪律已实际承压。

**修法**（P1）：CI 加双模板结构级比对（共享节标题集一致 + 红线条目数一致 + 关键锚点行逐字 diff；§四验证命令等已知有意差异处白名单豁免）。

#### D2（🟢）superpowers / dart-flutter 强耦合，无 standalone 形态

【代码走读】不装这两个插件的消费者，模板约 15% 内容是死引用（§二冲突裁决、§三 skill 映射、§十一速查表、skill 内 MCP 工具降级注）。设计方案已裁决「轻量模式不做」（触发线见 B3）——本评审**不推翻**，只建议低成本缓解：相关节头部加一行「未装 superpowers/dart-flutter 时本节可忽略」，速查表降级（B2）本身也消解大半。

#### D3（🟢）Windows hooks 静默失效，init 无显式警告

【代码走读】README 诚实声明了 macOS/Linux 限制，但 **Flutter 的目标平台含 Windows**——Windows 开发机上的 Flutter 团队拿到的是无闸版本，且 init/install 时**无一句警告**（静默降级）。

**修法**（P2）：install.sh / init.md 检测 `python3`/`fcntl` 不可用时输出一行显式降级警告（不阻塞安装）。

## 8 反向意见与不确定性声明（诚实边界）

1. **实验环境偏旧**：本机 Flutter 3.24.0 / Dart 3.5（2024-07 stable）。A1 的 `undefined_lint` 以 Dart 3.5 实测 + dart.dev 注册表（截至 3.13）双证，但**新版 analyzer 行为未实测**——若新版 Dart 收录了 `cancelled_token_use` 规则名（可能性低，官方清单无此名），A1 第 1 条降级为「版本敏感」。P0 执行时建议在最新 stable 复跑 §1 命令确认。
2. **token 估算口径**：本评审只引用 KB 实测（39.2/22.5/3.1/4.5），未直测 token 数——中文密度下 KB→token 换算不稳，B3 实测前勿把任何换算值当权威。
3. **C1/C2 为专业判断**：按包纪律标「需核验」，逐项查证（pub.dev 维护态 / 官方文档版本区间）后采信；本评审未预写坑卡正文，防「未查证预置」。
4. **B1 拆分的反面**：单 skill 的简单性（一个触发入口、一份 description 维护）是真实优点，拆分以触发面维护成本换加载精度——若真实试点（§4.8 观测）显示 skill 触发频率低、39KB 影响可忽略，B1 可降级为「只删通用内容、不拆文件」的折中档。
5. 本评审未复核 crules 母版侧的 deny-list fixture 质量（以 CI 同步比对步为准），未对 `docs/` 下设计方案/实施计划正文做逐条一致性核对（0.4.0 已两轮评审通过，不在本次范围）。
